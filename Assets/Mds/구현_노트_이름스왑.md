# 10. 맵 제작 방식 (확정)

## 10.1 방 = 독립 세트 (물리적 연결 안 함)
- 플레이어는 관리실 밖으로 안 나감 → 방들을 물리적으로 연결할 필요 없음.
- 각 방 = CCTV용 독립 세트. 서로 떨어뜨려 배치(오히려 작업/관리 편함).
- 귀신 이동 = 노드 순간이동(MoveToNode). 걸어가는 경로 불필요.
- 방 안 카메라(CAM01·02·05)는 방만, 복도 카메라(CAM03·04·06)는 복도만 봄 → 한 카메라가 방+복도 동시에 볼 일 없음.

## 10.2 복도 입구 처리 = "어둠" (방법 C 확정)
- **컨셉:** 불탄 독서실 → 문짝 타서 없음, 문틀 반쯤 부서짐, 입구 뻥 뚫림.
- 복도 CCTV로 보면 입구 너머가 보여야 자연스러움. 근데 실제 방을 붙이지 않음.
- **처리:** 입구 너머 = 얕게 판 검은 공간 + 그을음 + 잔해 실루엣 1~2개. 어둠에 잠겨 안 보임.
- "타서 뚫렸는데 안은 시커메서 안 보이는 입구" = 오싹함 + 독립성 유지.
- 실제 그 방(예: 공부방1)은 딴 데 따로, 해당 방 카메라(CAM01)가 담당.

## 10.3 텍스처/에셋 끼우는 법 (Phase 8, 걱정 해소용)
- **구조와 표면은 분리.** 지금 회색 박스로 구조(벽 위치·크기·물건 배치) 확정 → 나중에 표면만 교체.
- **텍스처:** 회색 큐브에 Material만 갈아끼움(모니터 Unlit처럼). 큐브 다시 안 만듦, 겉면만 바뀜.
- **에셋:** "책상 큐브" = placeholder → 나중에 진짜 책상 모델을 그 자리에 놓고 큐브 삭제.
- **조명+저해상도 필터**(Phase 8)로 최종 호러 룩.
- 무료 텍스처: ambientCG, Poly Haven, textures.com. 에셋: 스토어 office/school 팩.

# 11. 연호 종 메커니즘 (확정 — §7 열린 질문 해결)

## 11.1 결정: 인접 방 유인 (원작 FNAF3식)
- **종 = 연호를 뒤로 밀어내는 방어 도구** (조종 도구 아님 — 연호 무서움 유지).
- **인접 방에만 유인:** 연호 현재 위치와 직접 연결된 방에 종을 울려야 후퇴.
  - 엉뚱한(먼) 방에 울리면 → **헛방** (효과 없음, 종 횟수만 낭비).
- **효과:** 종 난 방(연호 뒤쪽)으로 유인 = 창문에서 멀어짐 = 후퇴.
- **핵심:** CCTV로 연호 위치를 정확히 파악해야 어느 방에 종 울릴지 앎 → 위치 추적 강제 → 긴장/공포.

## 11.2 왜 이 방식 (광역 밀어내기 폐기 이유)
- 광역이면 CCTV 안 봐도 종 연타로 대응 → 연호가 안 무서움.
- 인접 한정이면 연호를 계속 쫓아야 함 → 놓치면 헛방 → 메인 빌런의 압박 유지.
- 연호 정체성(항상 창문 수렴하는 정공법 빌런) 보호: 종으로 자유 조종 불가.

## 11.3 아직 구현 시 정할 것
- **유인 방식:** 루트 밖으로 끌기 X → **정해진 루트(노드) 상에서 뒤로 후퇴**. (연호는 노드 기반 이동)
  - 종 난 방이 연호 뒤쪽 노드면 유인 성공, 앞쪽/무관하면 헛방.
- **"인접" 판정:** 맵 인접관계를 종 로직에 반영 (연호 현재 노드의 이전 노드 = 유인 가능 대상).
- **거리별 후퇴량 / 무시 확률 1/7 / 창문 앞 무시 없음** 등은 기존 GDD 유지.
- 루트 다양화(L1~L3 + 추가)는 종과 별개로 계속 확장 가능 — 연호 다이나믹함은 행동 엔진(흉포 토글)에서 주로 나옴.

# 12. CCTV 카메라 에러 시스템 (신규 확정) + 현우 2스택 변경

## 12.1 카메라 에러 = 과사용 처벌 (FNAF3 비디오 에러 이식)
- **원작 확인:** FNAF3 카메라 에러 = CCTV를 너무 많이/오래 쓰면 발생. 화면이 스태틱으로 완전히 덮여 아무것도 안 보임(흐려짐이 아니라 완전 먹통). 귀신 위치 파악 불가. 단 **오디오(종)는 여전히 사용 가능**. 리셋 패널에서 camera system 리부팅(~5초).
- **우리 적용:**
  - **원인:** CCTV 과사용(너무 오래/자주 켜둠). "계속 감시 vs 과열 고장" 자원관리 긴장.
  - **효과:** CCTV 완전 먹통(스태틱). 귀신 위치 못 봄. **종은 계속 사용 가능**(원작대로).
  - **수리:** 리셋 패널에 **camera system** 항목 추가 → 5초 리셋.
  - **현우 무관:** 현우는 환풍구 집중, 카메라 에러는 순수 과사용 처벌(역할 분리).
- **결과:** 리셋 패널 = **audio / camera / ventilation 3종** = FNAF3 시스템 재시작 메뉴 완성.
  - (§8.1 에러 패널 UI가 이 3종 + reboot all + exit 항목)

## 12.2 현우 2스택 후폭풍 변경
- **기존:** 2스택 = CCTV 노이즈/지직(감시 방해). → **폐기**(카메라 에러와 역할 겹침).
- **변경:** 2스택 = **조명 나감**(관리실 어두워짐).
  - 1스택(조명 깜빡+시야 흐림) → 2스택(조명 완전히 나감) → 3스택(정전/배선고장).
  - 효과: 시각적 압박 확실 + **환풍구 불빛 버튼 확인 방해**(현우 코앞 대응 어려워짐) → 현우 대응 악화 = 긴장 고조.
- 현우 스택 최종: 1(조명 깜빡, 노랑) → 2(조명 나감, 주황) → 3(배선 고장/정전).

## 12.3 3종 에러 대칭 구조 (정리)
| 시스템 | 고장 원인 | 효과 | 수리 |
|---|---|---|---|
| Audio | 종 과사용(밤당 횟수 초과) or 현승 STRIKE1 | 종 못 씀 | 패널 리셋 5s |
| Camera | CCTV 과사용 | CCTV 완전 먹통(종은 가능) | 패널 리셋 5s |
| Ventilation | 김욱/준영 공격 | 화면 흐려짐 주기 반복 + 연호 흉포 | 패널 리셋 5s |
- 리셋: 개별 5s / 둘 8s / (reboot all은 추후). §3-b 리셋 시간과 통합 정리 필요.

# 13. 준영 재설계 (확정 — 창문 왼쪽 방해꾼)

## 13.1 결정: 창문 밖 왼쪽 실루엣 (원작 팬텀 포시 각도 반영)
- **출현:** 창문 **왼쪽 밖**에 실루엣으로 서 있음(창문 안쪽 아님, 바깥). 맵이 좁아 창문 밖 배치 가능.
- **방해 효과 (핵심):** 준영이 서 있으면 **현승/연호 창문 실루엣을 가림** → 창문 감시 방해.
  - 준영 하나가 현승 응시 대응 + 연호 종 대응을 동시에 방해 → 교란형의 이상적 형태.
  - "준영부터 치울까 vs 창문 지킬까" 딜레마.
- **대응:** 유예 시간 안에 **CCTV 켜면 사라짐**(안전). CCTV 켜기 = 정답 행동.
- **무시 시:** 대응 안 하고 딴 구역으로 시야 돌리면 → **armed** → 가운데(정면) 복귀 시(화면 전환) → **점프스케어**.
- **결과:** 교란형(즉사 아님) → **환기 오류 ON**(김욱과 동일 결과).

## 13.2 armed 판정 (CCTV 켜기와 충돌 방지)
- 준영 출현 = 아직 armed 아님, **유예 시간** 있음.
- 유예 안에 CCTV 켜기 → armed 되기 전에 사라짐(안전).
- 유예 안에 무시하고 딴 구역 돌림 → armed → 정면 복귀 시 점프.
- 즉 "CCTV 켜기"는 안전, "무시하고 구역 전환"만 armed. → ScreenTransitionDetector 공통 원리 사용하되 준영은 CCTV-down을 안전행동으로 예외 처리.

## 13.3 김욱과 대칭 유지
- 김욱: CCTV **안**에 나타남 → 카메라에서 **벗어나야** 안전.
- 준영: 창문 밖(CCTV 밖) → **CCTV를 켜야** 안전.
- 정반대 대응. 출현 확률: 3일 낮음(<1/50) → 5일 1/10. AI 없음(확률 출현), 하루 1회=점프 1회.

# 14. 현승 점프스케어 트리거 변경 (C안 — 원작 팬텀 프레디식 자동 발동)

## 14.1 변경 결정
- **기존(§0.5 통일):** armed → 화면 전환(CCTV/패널 올림·내림) 순간 STRIKE1.
- **변경(C안):** armed → **자동 타이머**(2~3초) → STRIKE1 자동 발동. 화면 전환 무관.
- **이유:** 원작 팬텀 프레디에 충실("숨었다가 몇 초 후 자동 점프"). "CCTV 켜자마자 즉발"의 어색함 제거. armed인데 CCTV 안 켜면 안 터지는 도망 구멍도 없음(자동이라).

## 14.2 연출 순서 (우리 현승 = 숨는 단계 없음)
- 우리 현승은 창문 워크패스(6초 가로질러 지나감)가 곧 응시 기회. 원작 프레디의 "바닥으로 숨는" 단계는 **우리엔 없음**.
1. 워크패스(창문 앞 6초 지나감) = 응시 기회.
2. 다 지나갈 때까지 응시 실패 → armed.
3. armed 후 **짧은 뜸(1~2초 정적, 긴장감용)** → 자동 발동. (숨는 연출 아님, 그냥 터지기 직전 정적)
4. 플레이어가 CCTV/패널 보고 있었으면 → **강제 정면 복귀**(jumpscare.Play() 내 ForceCancel 이미 구현됨).
5. 점프스케어(얼굴 확) → 오디오 고장.
- 짧은 뜸 없이 즉시 발동도 가능(프로토타입에서 택). 핵심은 화면 전환 대기 없이 자동.

## 14.3 구현 방향
- armed 되면 hideTimer 시작 → 끝나면 Strike1() 자동 호출.
- 현승은 ScreenTransitionDetector 구독 **제거**(자동 타이머로 대체).
- jumpscare.Play()의 ForceCancel(화면 강제 복귀)은 그대로 재사용 → 4번 연출.

## 14.4 §0.5 통일 규칙 → 캐릭터별 트리거로 조정 (중요)
- 원작도 캐릭터별로 트리거가 다름(프레디=자동/퍼펫=내릴때/포시=올리고 왼쪽/BB=노출시간). §0.5 "전 귀신 화면 전환 통일"을 일부 해제.
- **현승** = armed → 자동 타이머 발동(화면 전환 무관).
- **준영** = armed → 화면 전환(정면 복귀) 시 발동(§13).
- **연호** = 미정(구현 시 결정 — 창문 앞 armed + 화면 전환? 아니면 자동?).
- ScreenTransitionDetector는 준영 등 "전환 트리거 쓰는 귀신"용으로 유지. 현승은 미사용.
